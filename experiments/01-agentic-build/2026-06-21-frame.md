# Frame: Agentic Build

**Date**: 2026-06-21  
**Status**: problem framed clearly, iterating on proposal. System not yet live. 

## 30-second skim

**Truffle now has more good improvement ideas than Brian is struggling to act on and personally sequence by hand.** Market Read Lab produced a useful queue: cohort discovery, denominator receipts, signal confound rules, small lints, targeted backfills. The risk is not lack of ideas; it is turning every idea into either a sprawling design session or a half-reviewed agent patch.

**Agentic Build is the missing operating loop:** a small, file-backed way to let agents frame, propose, review, revise once, implement, review again, and then hand Brian a short decision surface.

It should not be an all-or-nothing batch ritual. The same safety pattern needs to scale down to one change when that is all the work needs.

The job is to **make agent delegation feel calm & trustworthy.**

## Why This Matters

Brian wants agents to improve the system on their own - to **increase velocity** and let him focus on other things - without letting Truffle get out of hand.

He does not want agents to significantly alter key schemas, introduce or alter key architectural patterns, or add new persistent entities or judgment-heavy primitives unless he has a real understanding and is in full agreement. But he wants to allow small, low-risk, "quick wins" to get made easily and quickly, with just light involvement from him.

He also wants the learning preserved when a solution gets rejected - and not lose track of important problems that **should** be solved - even if we don't know the right solution yet.

That combination needs an explicit middle layer between "ask one agent to do the task" and "build a fully autonomous agentic development and project-management system." The middle layer should keep the problem frame durable, let multiple solutions be considered, and give an agent authority to cut proposals before they become code.

It also needs to work at different weights. A full batch cannot be the only entry point.

## What Makes It Hard

Agents are good at motion and bad at restraint unless the contract is visible.

- A worker implements before clarifying the problem.
- A reviewer reviews only correctness, not scope.
- Changes that make sense in isolation - but not when you consider the full system.
- Multiple workers edit the same files.
- A useful frame gets discarded because the first proposal was wrong.
- Brian receives too much detail at the end and gets overwhelmed - and "proposals" / work batches stall in the human review step.
- Safeguards get bundled as one heavy ritual, so small changes either overpay or skip them.

The workflow should prevent those without becoming ceremony.

## Capability Goal

The **long term vision** is a way for agents to build and improve Truffle mostly on their own - with Brian involved only for the most important, risky or ambiguous changes.

Short term, the system should achieve:

**Must Have**

- **"Wallow"**: Agents can gather project context, gather evidence from prior experiments or Market Read Lab Runs, and write up a problem statement for a clear chunk of work in a short **"Frame" doc**.
- **"Prototype"**: Agents can brainstorm, do web research on potential solutions / tools / patterns to leverage, run mini-experiments, and converge on a short **"Proposal" doc**.
- **Brian is not a required reviewer** in these individual "change packet" frame + proposal steps. 
- **Single-change use**: Agents can apply the same core discipline to one bounded change without requiring a multi-packet batch.
- **Implementation**: Agents can implement accepted proposals without requiring Brian's involvement in every packet. When the stakes are high, unclear, or architectural, they should escalate rather than guess.
- **Staging**: Proposed changes do not enter the "live" Truffle system until approved. Brian should be able to keep using Truffle - running verbs, routines, and Market Read Lab - without accidentally using unapproved changes still in “staging”. Generated artifacts can stay inside the packet's working area.
- **Cut / veto authority**: An agent can stop a packet before implementation if the problem is not worth solving now, the proposal is too risky, or the work would make Truffle less coherent.
- **Rejected-learning preservation**: A cut packet still leaves behind the frame, why the solution was rejected, and what evidence would revive it later.
- **Simplicity first**: The system should reward / push for the simplest, most elegant solution possible - and protect against agents overcomplicating things.

**Should Have**

- **Agentic Proposal Review**: A separate agent (that did not develop the proposal) reviews the proposal before agents move to implementation, using criteria stated in the packet's frame and higher-level Truffle principles.
- **Optional Frame Review**: Risky or strategically ambiguous packets can get a separate frame review before proposal work begins.
- **Risk Buckets**: Packets should carry a coarse risk class so low-risk changes move quickly and high-risk changes slow down. Definitions should guide behavior while evolving as trust improves.
- **Spend Awareness**: Packets using web research, paid captures, or external APIs should have a visible budget and stop condition during development and/or evaluation. The goal is bounded autonomy, not granular bureaucracy.
- **Composable judgment steps**: Framing, proposal review, patch review, and cut/park decisions can be used independently when a change only needs part of the loop. 
- **Learning loop**: The agentic build system should have a way to learn & improve itself when a change run / loop doesn’t go well. State style files should accumulate verified facts. Evaluation / review runs should refine prompts and rubrics, and/or the skill that produced it.

## Non-Goals

- No intricate new task tracker.
- No automatic merge without review. 
- No standing service, graph, or database.
- No guarantee every packet ships.
- No requirement that every change become part of a batch.
- No schema, taxonomy, entity, or judgment persistence unless explicitly framed and approved by Brian.
- No permanently maintained checklist of every possible escalation rule. The system should teach agents how to judge risk, not force Brian to maintain brittle policy tables.

## Constraints

Keep the workflow file-first and low-infra. Folders and markdown are enough for v0.

Protect Truffle's existing boundaries: store State stays evidence-backed, Signals stay source-grained and separated from State, Judgments stay labeled and likely project-side, and Market Read Lab outputs / suggestions do not graduate automatically.

Brian's final review should be a **short decision surface**, not a pile of agent transcripts.

The approval model should be expected to evolve. Early batches may involve Brian heavily. As the workflow earns trust, more decisions can move to agent review and lead-agent judgment.

Small changes should not pay the coordination cost meant for parallel or ambiguous work. The system should let Brian choose the smallest trustworthy review surface for the change at hand.

## Initial Scope

Start with one top-level operating experiment under `experiments/01-agentic-build/`.

Then test it on both a single bounded change and a small batch. If the workflow feels heavy, cut steps. If it feels loose, add structure only where the run showed a real failure.

## Success Criteria

- Brian can keep using live Truffle while packet work happens elsewhere.
- Brian can approve, reject, or ask for revision from a short decision surface appropriate to the size of the change.
- Review catches scope creep before implementation, especially around schema, architecture, persistence, and judgment-heavy changes.
- Small changes can use the relevant safety steps without invoking a full batch.
- Rejected packets still improve the system's understanding of the problem.
