# Proposal: Agentic Build v0

Date: 2026-06-21  
Status: proposed operating model

## Short Answer

Agentic Build should be packet-first, not batch-first.

A **"change packet"** is one bounded proposed improvement with just enough framing,
proposal, review, and decision record to keep agents from drifting. A **"build batch"**
is only a wrapper around multiple change packets when grouping or parallelism is useful.

Normal agent work remains the default for obvious low-risk changes. Use a change packet
when the work needs preserved reasoning, proposal review, staging, or a cut/park record.

## Core Terms

- **"Change packet"** - one bounded proposed change to Truffle. It may ship, park, or get cut.
- **"Build batch"** - two or three change packets coordinated together because their timing,
  write sets, or final review should be managed as one effort.
- **"Decision surface"** - the short human-facing summary that says what to merge, hold,
  revise, park, or cut.

## When To Use It

Skip Agentic Build for tiny changes where the request, scope, and verification are obvious.

Use a **"change packet"** when any of these are true:

- The problem needs to be framed before implementation.
- Multiple plausible solutions deserve comparison.
- The change touches engine rules, prompts, scripts, workflow conventions, or durable docs
  that change how Truffle is run.
- Rejection would still produce useful learning.
- Spend, live evidence, schema risk, persistence, automation, or project write-back might enter.

Use a **"build batch"** only when several change packets benefit from coordination. Batches
are for disjoint parallel work, shared staging, or one combined human review.

## File Shape

Keep the file shape light and let the first runs prove what earns its keep.

```text
experiments/01-agentic-build/
  README.md
  2026-06-21-frame.md
  2026-06-21-proposal.md
  changes/
    YYYY-MM-DD-short-name/
      frame.md
      proposal.md
      proposal-review.md
      lead-decision.md
      implementation-notes.md
      packet-review.md
  batches/
    YYYY-MM-DD-short-name/
      batch-plan.md
      decision-surface.md
      changes/
        01-short-name/
          frame.md
          proposal.md
          proposal-review.md
          lead-decision.md
          implementation-notes.md
          packet-review.md
```

Files are created when that stage runs. Do not create templates until repeated use shows
which fields agents actually need.

## Change Packet Minimums

Each `proposal.md` should include five blunt fields before the option analysis:

- `risk` - `low`, `medium`, or `high`.
- `allowed_write_paths` - the files or directories the worker expects to touch.
- `spend_stop` - live evidence, paid capture/API spend, and the stop condition.
- `acceptance_checks` - the goal contract: what must be true, how to verify it, and
  where the evidence or receipt will live.
- `escalate_if` - conditions that move the packet back to the lead or Brian.

## Goal-Driven Execution

Every packet should turn the requested change into a checkable goal before implementation.
For code, verification can be tests, lints, fixtures, or smoke runs. For prompts, skills,
templates, or doc packets, use a receipt: the scenario tried, the expected behavior, and
the artifact path that proves it. If the worker cannot state a checkable goal without
guessing, stop and escalate instead of implementing.

## Change Packet Lifecycle

1. **Frame.** State the problem, constraints, non-goals, and success condition.
2. **Proposal.** Name assumptions, compare 2-3 options including the smallest viable one,
   and recommend one.
3. **Proposal review.** A separate reviewer critiques before implementation when the packet
   is medium/high risk, strategically ambiguous, or likely to create drift.
4. **Lead decision.** Accept, request one revision, park, or cut.
5. **Revision, optional.** One pass only.
6. **Implementation.** Edit only the accepted scope.
7. **Patch review.** Audit the patch against the accepted proposal and acceptance checks.
8. **Decision surface.** Say what should merge, hold, revise, park, or cut.

A packet can stop at any stage. Stopping is not failure if the reason and revival condition
are preserved.

## Roles

**Lead agent**

- Owns scope, risk, and the final decision surface.
- Sets or confirms `risk`, `allowed_write_paths`, and spend posture.
- Accepts, requests one revision, parks, or cuts packets.
- Applies accepted work to the live checkout only after review and approval.

For a single low-risk change packet, the current agent may wear the lead role. For a build
batch, the lead role should be explicit.

**Worker agent**

- Writes the frame and proposal.
- States risk, allowed write paths, spend, stop condition, escalation triggers, and checks.
- Implements only after lead acceptance.
- Writes implementation notes.

**Reviewer agent**

- Reviews proposals for scope creep, schema risk, hidden infrastructure, persistence
  boundary drift, weak evidence, vague acceptance checks, and dishonest risk/spend.
- Reviews patches findings-first, with attention to tests/checks, conflicts, blast radius,
  and whether the patch still matches the accepted proposal.

## Decision Rules

Lead decisions should be blunt:

- `accept-for-implementation` - proposal is narrow enough to build.
- `revise-once` - promising, but unclear or too broad.
- `park` - good idea, wrong time or missing evidence.
- `cut` - violates constraints or is not worth doing.
- `merge` - implemented and reviewed.
- `hold-after-review` - implemented but not ready to merge.

A parked or cut packet must preserve the decision reason and `revive_if`: the evidence,
timing, or constraint change that would make it worth reopening.

## Staging Model

Packet work happens outside live Truffle usage. Brian should be able to keep running verbs,
routines, and Market Read Lab without accidentally consuming unapproved changes.

Default v0 staging: implementation happens in an isolated git worktree or as a patch
artifact inside the packet folder. The lead applies accepted work to the live checkout
only after patch review, decision-surface approval, and any needed conflict check.

Generated artifacts are allowed if they stay inside the packet's working area. Nothing becomes
part of the live engine, live store contract, scheduled routines, or project write-back flow
until it appears in the decision surface and is approved.

## Risk + Spend

Use coarse, revisable buckets rather than a brittle policy table:

- `low` - docs, recipes, and small local-only cleanup that do not alter contracts or live
  behavior.
- `medium` - committed scripts, tools, lints, tests, or existing-convention backfills.
- `high` - schema/taxonomy/store-contract changes, automation, write-back paths, persistent
  entities, or anything that could alter live Market Read Lab behavior.

Workers should name expected live evidence, paid capture/API spend, and stop conditions in
the proposal. In v0, high-risk packets are planning-only until Brian explicitly approves
implementation. Unclear risk defaults to high.

## Build Batch Wrapper

A **"build batch"** adds only the coordination that multiple change packets need:

- `batch-plan.md` names why the packets are grouped, the rough risk posture, write sets,
  and any shared staging rule.
- Keep batches to three change packets by default.
- Packet write sets should be disjoint, or the batch should use isolated worktrees.
- The lead integrates accepted change work and writes one `decision-surface.md`.

Do not run a build batch when one change packet would do.

## Guardrails

- Prefer the smallest trustworthy review surface for the change.
- One revision phase per packet.
- Proposal fields: `risk`, `allowed_write_paths`, `spend_stop`, `acceptance_checks`,
  and `escalate_if`.
- No new persistent Truffle entities, category objects, schema fields, monitor services, or
  write-back automations unless the packet explicitly frames the risk and escalates it.
- In v0, `high` risk means plan/review only until Brian explicitly approves implementation.
- Parked or cut packets need a decision reason and `revive_if`.
- When a packet is warranted, prefer docs, recipes, small lints, and existing-convention backfills.

## First Exercises

Test the workflow with one low-risk change packet before running a build batch.

The first batch should be chosen separately. This proposal should define the operating model,
not lock in the first work queue.

## Success Criteria

- A single bounded change can use the safety loop without becoming a batch.
- Brian can approve, reject, or ask for revision from a short decision surface.
- Review catches scope creep before implementation, especially around schema, architecture,
  persistence, automation, and judgment-heavy changes.
- Rejected packets still improve the system's understanding of the problem.
