# Proposal: Agentic Build v0

Date: 2026-06-21  
Status: proposed operating model, in review.

## Short Answer

Agentic Build should be “packet-first”, not batch-first.

A **"change packet"** is one bounded proposed improvement with just enough framing,
proposal, review, and decision record to keep agents from drifting. A **"build batch"**
is only a wrapper around multiple change packets when coordination is useful.

Normal agent work remains the default for obvious low-risk changes. Use a change packet
when the work needs preserved reasoning, proposal review, staging, or a cut/park record.

## Core Terms

- **"Change packet"** - one bounded proposed change to Truffle. It may ship, park, or get cut.
- **"Build batch"** - two or three change packets coordinated together because their timing, write sets, or final review should be managed as one effort.
- **"Decision surface"** - the short human-facing summary that says what to merge, hold, revise, park, or cut.

## When To Use It

Skip Agentic Build for tiny changes where the request, scope, and verification are obvious.

Use a **"change packet"** when any of these are true:

- The issue / problem statement is not extremely clear, or needs to be framed before implementation.
- Multiple plausible solutions deserve comparison.
- The change touches prompts, key scripts, workflow conventions, or durable docs that change how Truffle is run.
- The change pushes the edges of the system, or local principles do not clearly cover it.
- Rejection would still produce useful learning.
- Spend, live evidence, schema risk, persistence, automation, or project write-back might enter.

Use a **"build batch"** when several change packets benefit from coordination. Batches are for disjoint parallel work, shared staging, or one combined human review.

## File Shape

Keep the file shape light and let the first runs prove what earns its keep.

```text
experiments/01-agentic-build/
  README.md
  2026-06-21-frame.md
  2026-06-21-proposal.md
  2026-06-21-lead-context.md
  changes/
    YYYY-MM-DD-short-name/
      frame.md
      proposal.md
      proposal-review.md

      packet-review.md
  batches/
    YYYY-MM-DD-short-name/

        01-short-name/
          frame.md
          proposal.md
          proposal-review.md
          lead-decision.md
          implementation-notes.md

```

Files are created when that stage runs. Low-risk packets may combine frame context
inside `proposal.md` instead of creating a separate `frame.md`. Do not create templates
until repeated use shows which fields agents actually need.

## Change Packet Minimums

Each `proposal.md` should include five blunt fields before the option analysis. If
a field cannot be known yet, say `unknown` and why.

- `risk` - `low`, `medium`, or `high`.
- `write_scope` - expected files, directories, or boundaries the worker expects to touch.
- `spend_stop` - live evidence, paid capture/API spend, and the stop condition.
- `acceptance_checks` - the goal contract: what must be true, how to verify it, and
  where the evidence or receipt will live.
- `escalate_if` - conditions that move the packet back to the lead or Brian.

## Goal-Driven Execution

Every packet should turn the requested change into a checkable goal before implementation.
For code, verification can be tests, lints, fixtures, or smoke runs. For prompts, skills,
templates, or doc packets, use a receipt: the scenario tried, the expected behavior, and
the artifact path that proves it. If the worker cannot state a checkable goal without
guessing, stop and escalate instead of implementing.

## Change Packet Lifecycle

1. **Frame.** State the problem, constraints, non-goals, and success condition. Keep it as short as the problem allows.
2. **Proposal.** Name assumptions, compare 2-3 options including the smallest viable one, and recommend one. Low-risk packets may combine frame + proposal in one short doc when the scope is clear.
3. **Proposal review.** A separate reviewer critiques before implementation when risk, ambiguity, or drift warrants it.
4. **Lead decision.** Accept, request one revision, park, or cut.
5. **Revision, optional.** One pass only.
6. **Implementation.** Edit only the accepted scope.
7. **Patch review.** Audit the patch against the accepted proposal, acceptance checks, and repo-wide rules.
8. **Decision surface.** Say what should merge, hold, revise, park, or cut.

A packet can stop at any stage. Stopping is not failure if the reason and revival condition
are preserved.

## Roles

**Lead agent**

- Owns scope, risk, and the final decision surface.
- Sets or confirms `risk`, `write_scope`, and spend posture.
- Accepts, requests one revision, parks, or cuts packets.
- Applies accepted work to the live checkout only after review and approval.

For a single low-risk change packet, the current agent may wear the lead role. For
a build batch, the lead role should be explicit.

**Worker agent**

- Writes the frame and proposal, or a combined low-risk proposal when appropriate.
- States risk, write scope, spend, stop condition, escalation triggers, and checks.
- Implements only after lead acceptance.
- Writes implementation notes.

**Reviewer agent**

- Reviews proposals for scope creep, schema risk, hidden/new living infrastructure, persistence boundary drift, weak evidence, vague acceptance checks, and dishonest risk/spend.
- Reviews patches findings-first, with attention to tests/checks, conflicts, blast radius, and whether the patch still matches the accepted proposal.

Agent self-critique is NOT sufficient. Sub-agents / separate sessions are required for review. Must use an independent judge / verifier. 

## Decision Rules

Lead decisions should be blunt:

- `accept-for-implementation` - proposal is narrow enough to build.
- `revise-once` - promising, but unclear or too broad.
- `park` - good idea, but wrong time, missing evidence, or unsatisfactory / overly complex implementation.
- `cut` - violates constraints or is not worth doing.
- `merge` - implemented and reviewed.
- `hold-after-review` - implemented but not ready to merge.

A parked or cut packet must preserve the decision reason and `revive_if`: the evidence, timing, or constraint change that would make it worth reopening (if any). 

## Staging Model

Packet work happens outside live Truffle usage. Brian should be able to keep running verbs,
routines, and Market Read Lab without accidentally consuming unapproved changes.

Default v0 staging: code or live-behavior changes happen in an isolated git worktree.
Docs-only or generated artifacts may use a patch artifact inside the packet folder.
The lead applies accepted work to the live checkout only after patch review,
decision-surface approval, and any needed conflict check. The lead's work should
not disturb the local master branch, which is shared with Brian.

Generated artifacts are allowed if they stay inside the packet's working area. Nothing becomes part of the live engine, live store contract, scheduled routines, or project write-back flow until it appears in the decision surface and is approved.

## Risk + Spend

Workers should name expected live evidence, paid capture/API spend, and stop conditions in
the proposal. Current risk calibration, approval posture, and risk-handling defaults live in
[`2026-06-21-lead-context.md`](2026-06-21-lead-context.md).

## Build Batch Wrapper

A **"build batch"** adds only the coordination that multiple change packets need:

- `batch-plan.md` names why the packets are grouped, the rough risk posture, write sets,
  and any shared staging rule.
- Keep batches to 2-3 change packets by default.
- Packet write sets should be disjoint, or the batch should use isolated worktrees.
- The lead integrates accepted change work to one worktree and writes one `decision-surface.md`.

Do not run a build batch when one change packet would do.

## First Exercises

Test the workflow with one low-risk change packet before running a build batch.

The first batch should be chosen separately. This proposal should define the operating model, not lock in the first work queue.

## Success Criteria

- A single bounded change can use the agentic development and safety loop without becoming a batch.
- Brian can approve, reject, or ask for revision from a **short**, plain English decision surface - that makes it easy for him to dig deeper / look under the hood when desired.
- Review catches scope creep before implementation, especially around schema, architecture, persistence, automation, and judgment-heavy changes.
- Rejected packets still improve the system's understanding of the problem.
