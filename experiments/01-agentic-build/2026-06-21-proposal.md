# Proposal: Agentic Build v0

Date: 2026-06-21  
Status: proposed operating model

## Short Answer

Use **Agentic Build** as a lightweight batch workflow for parallel agent work. It should produce better patches and better rejected learning without creating a heavy new system to maintain.

The lead agent owns decomposition, scope, integration, and cuts. Worker agents own packet frames, proposals, and implementations. Reviewer agents audit proposals and implemented patches. Brian only reviews the final merge docket.

### Overview

A reusable **build batch** pattern:

- The lead agent decomposes work into 3 or fewer packets.
- Each worker writes a short frame and proposal before implementation.
- A separate reviewer critiques the proposal; risky frames may get reviewed earlier.
- The worker gets at most one revision phase.
- The lead can accept, park, or cut the packet.
- Accepted packets get implemented, reviewed, and summarized in a one-page merge docket.

## Folder Shape

```text
experiments/01-agentic-build/
  README.md
  2026-06-21-frame.md
  2026-06-21-proposal.md

    YYYY-MM-DD-short-name/

          frame.md
          proposal.md
          proposal-review.md
          lead-decision.md
          implementation-notes.md

```

Do not create templates until the first batch proves which files earn their keep.

## Roles

**Lead agent**

- Writes `batch-plan.md`.
- Assigns packets with disjoint write sets.
- Sets the packet's rough risk class and spend posture.
- Reads proposal reviews.
- Accepts, requests one revision, parks, or cuts packets.
- Integrates accepted work.
- Writes `merge-docket.md`.

**Worker agent**

- Creates the packet folder.
- Writes `frame.md` using the Frame skill.
- Brainstorms options inside `proposal.md`.
- Recommends one solution.
- States expected spend, live evidence needs, and implementation risk.
- Revises once if asked.
- Implements only after lead acceptance.
- Writes `implementation-notes.md`.

**Proposal reviewer**

- Reviews the proposal before implementation.
- Looks for scope creep, schema risk, hidden infrastructure, bad persistence boundaries,
  weak evidence, unclear acceptance checks, and whether risk/spend are named honestly.
- Recommends: accept, revise once, park, or cut.

**Implementation reviewer**

- Reviews the implemented patch.
- Findings first.
- Confirms tests/checks.
- Flags blast radius, conflicts, and whether the patch still matches the accepted proposal.

## Packet Lifecycle

1. **Frame.** Worker states the problem, constraints, non-goals, and success condition.
2. **Proposal.** Worker compares 2-3 options and recommends one.
3. **Optional frame review.** Trigger when the packet is strategically ambiguous, high-risk,
   or likely to create system drift.
4. **Proposal review.** Reviewer critiques before code exists.
5. **Lead decision.** Lead accepts, requests one revision, parks, or cuts.
6. **Revision, optional.** One pass only.
7. **Implementation.** Worker edits only the accepted scope.
8. **Implementation review.** Reviewer audits the patch.
9. **Merge docket.** Lead tells Brian what to merge, hold, or reject.

## Decision Rules

Lead decisions should be blunt:

- `accept-for-implementation` - proposal is narrow enough to build.
- `revise-once` - promising, but unclear or too broad.
- `park` - good idea, wrong time or missing evidence.
- `cut` - violates constraints or is not worth doing.
- `merge` - implemented and reviewed.
- `hold-after-review` - implemented but not ready to merge.

Cutting is a feature. A cut packet still leaves behind a useful problem frame and a record
of why that solution failed.

## Staging Model

Packet work happens outside live Truffle usage. Brian should be able to keep running verbs,
routines, and Market Read Lab without accidentally consuming unapproved changes.

Generated artifacts are allowed if they stay inside the packet's working area. Nothing becomes
part of the live engine, live store contract, scheduled routines, or project write-back flow
until it appears in the merge docket and is approved.

## Risk + Spend

Use coarse, revisable buckets rather than a brittle policy table:

- `low` - docs, templates, recipes, and small local-only cleanup.
- `medium` - committed scripts, tools, lints, tests, or existing-convention backfills.
- `high` - schema/taxonomy/store-contract changes, automation, write-back paths, persistent
  entities, or anything that could alter live Market Read Lab behavior.

Workers should name expected live evidence, paid capture/API spend, and stop conditions in
the proposal. High-risk or unclear packets escalate under the current batch policy; in v0,
that usually means Brian sees them before implementation or merge. As trust improves, the
lead/reviewer can carry more of that judgment.

## First Batch Recommendation

Start with **3 packets**:

1. `cohort-discovery-verb` - turn the existing cohort discovery experiment into a clearer
   reusable verb/workflow recommendation. No durable cohort object.
2. `denominator-and-capture-candidate-receipts` - update Market Read Lab templates so reads
   preserve denominator method, store hit/miss diff, and suggested captures.
3. `signal-confound-rules` - document recurring signal anti-footguns in `QUERYING.md` or the
   nearest existing read guide.

Hold for batch two:

- `sec_edgar` delta branch.
- `captured_at` normalization or lint.
- targeted depth backfills.

## Guardrails

- Three packets per batch by default.
- Disjoint write sets.
- One revision phase.
- No new persistent Truffle entities, category objects, schema fields, monitor services, or
  write-back automations unless the packet explicitly frames the risk and escalates it under
  the current batch policy.
- Prefer docs, recipes, small lints, and existing-convention backfills.

## Success Criteria

The first batch succeeds if Brian can approve or reject all packet outcomes from a short
merge docket without reading every worker transcript.

If a packet is cut or parked, the reason and revive condition are preserved.
