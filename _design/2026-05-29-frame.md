# Frame: a global company-research engine

> **Goal.** Turn *"research company X"* into reliable, cached, structured intelligence that **any project can read and any agent can query** — using Firecrawl for capture (not lazy, blocked, or JS-walled WebSearch) and Claude Max for reasoning (no per-call LLM economics).

*Wallowing-stage Frame, per [Core: How We Work](https://www.notion.so/a4b0fd75ea984d66b8c3f849f1c8f838). Feels out the **problem** space — objectives, scope, principles, open questions — not the solution. Name: **web-research**.*

## TL;DR

- **What.** A project-agnostic toolbox of company-research capabilities. The unit of reuse stops being "a Teleprescribe workflow" and becomes "a capability *any* project calls."
- **The bet.** Capture is already solved (agent-workflows proved it). **Queryability is the product** — the thing that doesn't work today.
- **The payoff loop.** A company captured once (for Teleprescribe) is warm and nearly free for the next project (new SaaS tool, a PE look, anything).
- **The discipline.** *Spend on conventions, not infrastructure.* Stay file-first; earn every piece of structure.

## Why this exists

Two prior systems each got half of it right. This takes the substrate from one and the good ideas from the other, drops the weight of both, and makes it global.

<details>
<summary>The gap between Doro and agent-workflows</summary>

| | Proved | Weakness |
|---|---|---|
| **Doro** | The *intellectual core* — provenance, freshness, structure-at-ingestion, "structure for retrieval" | Heavy infra (Postgres/Neo4j/S3/Temporal); per-call LLM economics; taxonomy + entity-resolution machinery |
| **agent-workflows** | The *substrate* — markdown/git/Notion + Claude Code/Routines, Max-absorbed cost. | Bound to one venture's domain + KB; **no query layer** — agents grep from scratch, only if told |
| **web-research** | Substrate + core ideas, kept light, made **global** | TBD — the job of this Frame is to keep it from re-becoming Doro |

</details>

> **The one tension to manage.** Every new ambition (product-level analysis, cross-brand aggregation, market maps) pulls *toward* Doro's structured knowledge graph. The substrate philosophy pulls *toward* agent-workflows' lightness. **You already shut Doro down once.** When a decision smells like the heavy column above, that's the red flag.

## Architecture

Two orthogonal "threes." Don't conflate them — one is about *where things live*, the other about *who owns structure*.

**Three layers — where things physically live**

| Layer | What | Lives in |
|---|---|---|
| **Verbs** | Skills / slash commands (`/research-company`, …) | Global `~/.claude/skills/` |
| **Engine + Store** | Capture/clean scripts, the shared store, default schema | This repo (own remote + iCloud) |
| **Project config** | Schema overrides, source ranking, freshness, destination | `.web-research/config.yaml` per project |

*A global skill reaches the engine via `WEB_RESEARCH_HOME` in `~/.claude/settings.json` — the same file that grants repo access + allowlists `api.firecrawl.dev`. Config resolves as **global defaults ← project overrides.***

**Three tiers — who owns the structure**

| Tier | What | Owner |
|---|---|---|
| **0 — Engine core** | Identity, capture-meta, nav/key-pages, description, favicon, generic classification | Engine, always |
| **1 — Opt-in generic** | Brand profile, product index — generic *in form*, toggled per project | Engine ships, project enables |
| **2 — Project taxonomy** | Verticals, "direct competitor?", destination mapping | Project, user-driven |

> **The guardrail.** The engine owns generic **capabilities** and cross-domain taxonomies (Tier 1). It never owns **project-specific verticals** (Tier 2). "Offering type" is generic; "Weight Loss" is a project opinion. This keeps Doro's per-market taxonomy + normalization machinery out.

<details>
<summary>Domain-as-entity-key — the shortcut that deletes Doro's hardest problem</summary>

Doro's most expensive subsystem was **entity resolution** (RapidFuzz + embeddings + LLM judgment to decide "is this the same company?"). For companies we mostly don't need it: **the canonical domain is the unique key.** The store keys on domain slug; identity reconciliation disappears.

Edge cases — rebrands, M&A, multi-domain — are handled by a thin `aliases:` list in frontmatter, not a resurrected embedding pipeline.

</details>

## The store

One company = one folder = its whole story. **Top-level docs are the latest view** — you rarely open `captures/`. No symlink (fragile across iCloud + git + cloud); a `captured_at` field is the freshness pointer.

```
store/<domain-slug>/              # e.g. hone-health
  profile.md                      # Tier-0 core (Synthesis) — frontmatter + body
  brand.md                        # Tier-1, opt-in (separate doc)
  offerings.md                    # Tier-1, opt-in (separate doc)
  captures/
    2026-05-29/                   # one self-contained folder per run
      homepage.md  pricing.md     # cleaned observations (Capture)
      .payloads/                  # raw Firecrawl JSON + screenshots (gitignored, pruned)
    _archive/                     # old runs swept here to keep latest obvious

cohorts/<category-slug>/          # (later, tbd) cross-company signals that don't key on a domain
```

- **Top = Synthesis, `captures/` = Capture.** agent-workflows' vocabulary made spatial.
- **Tier-1 modules are separate docs**, not sections — cleaner opt-in, cleaner per-module freshness.
- **Payload sidecars are write-once durable inputs** — gitignored, iCloud-synced, progressively pruned. Retroactive work reads sidecars before re-fetching.
- **Two entity types by design** — companies (domain) and cohorts (category slug). v1 is company-only.

## Frontmatter: think in field *types*, cut hard

> **Principle.** Frontmatter = stable + queryable + cheap. Body = the meat (nav tree, descriptions, observations). **Derive, don't store, anything the domain gives you for free.**

```yaml
domain: honehealth.com            # primary key
name: Hone Health
aliases: []                       # alt names/domains; rebrand + M&A escape hatch
captured_at: 2026-05-29
capture_method: firecrawl
description: "DTC men's-health brand offering TRT and longevity programs."
tags: [telehealth, mens-health]   # freeform, NOT a taxonomy
key_pages:                        # semantic distillation of the nav
  pricing: /pricing
  about: /about
  blog: /blog
site_notes: "cloudflare-fronted; pricing lives on product pages, not /pricing"
# favicon + website_url are DERIVED from domain, never stored
```

*`site_notes` (the carry-forward agent playbook) was the quiet MVP of competitive-intel — it's how the next capture inherits the playbook instead of re-discovering it.*

<details>
<summary>Full field-type map — what to keep, derive, and cut from Doro's schema</summary>

| Type | Fields | Verdict |
|---|---|---|
| **Identity** (PK, stable) | `domain`, `name`, `aliases` | **keep — core** |
| **Capture meta** | `captured_at`, `capture_method`, `site_notes`, `key_pages`, `unverified_fields` | **keep — core** |
| **Computed-from-domain** | favicon, website_url, homepage | **derive, don't store** |
| **Generic descriptive** | `description` | **keep — core** |
| **External links** | `linkedin`, `x`, `wikipedia` | optional — deep-research handoff hook |
| **Generalizable categorical** | `entity_type`, `target_market`, `offering_category`, `portfolio_shape`, `business_model`, `primary_industry` | **in scope** — small generic closed sets ([`TAXONOMIES.md`](../TAXONOMIES.md)). `lifecycle_stage` **cut** — a deep-research signal, not website-determinable. |
| **Structured nav** | full nav tree | keep, but **body/sidecar, not frontmatter** — only the semantic distillation (`key_pages`) lifts up |
| **Identity validation** | `identity_validation_score`, `validation_metadata` | **cut** — Doro *discovered* companies; you *hand it a domain* |
| **Datapoint provenance** | per-field confidence, reconciliation | **cut** — section-level `captured_at` is enough |
| **Resolved relationships** | `competitors`/`parent` as UUID objects | **cut** — freeform names if useful; no relationship graph |

</details>

## Queryability — a ladder, cheapest rung first

The agent-workflows failure wasn't "no database." The frontmatter was *there*; there were no tools and agents started from scratch. That's a **tooling + discoverability** problem, not a storage one.

| Rung | What | When |
|---|---|---|
| **1. Disciplined frontmatter** | One consistent, documented YAML schema | now — ~free |
| **2. Query affordance** | A documented access pattern + thin helper, wrapped in a skill the agent *knows* to reach for | **the likely actual fix** — literal form determined in the prototyping stage |
| **3. Derived index** | SQLite/JSONL built *from* the markdown — a regenerable cache, never source-of-truth | medium-term, with the first cross-company aggregation |

> Foundation lives at **rungs 1–2.** Rung 3 arrives with aggregation (sooner than "someday") but stays a derived cache off good frontmatter — a `generate` step, never a migration. *That's* why the frontmatter discipline is worth the spend now.

## Deep research is a consumer, not a tenant

This system is the **foundation / priors layer.** An open-ended deep-research run (news, funding, M&A, reviews) is a *different, project-specific job* that **reads the foundation first**, then goes wide.

- **Store stays tight and factual.** We do NOT dump news/funding into the profile — that's the "ingest everything into a graph" move that made Doro heavy. Resist it.
- **Deep-research output lives project-side**, not in this store. The store gives priors; the project keeps the narrative.
- **The store must be legible to an arbitrary agent** so deep-research reads it before re-scraping. Reinforces rung 2.

## Scope & phasing

> **v1 = on-demand single-company dossier.** `/research-company <domain>` → map → scrape key pages (cache-aware via freshness) → write `store/<domain>/profile.md`. **The store entry IS the dossier** — no separate artifact. A cold session reads that one file and answers.

| Phase | Delivers | Horizon |
|---|---|---|
| **Foundation** | Single-company dossier; rungs 1–2 | now |
| **Aggregation** | Cross-brand queries ("group Sermorelin across brands"); rung 3 | medium |
| **Visualization** | Market maps, 2x2s, battle maps (crowdedness / dominance / hotness) | long |

*Visualizations are pull-consumers — but they impose requirements backward: hotness needs traction signals, so **traction is first-class, not a bolt-on**, even though the maps themselves are far off.*

## Non-goals — the anti-Doro guardrails

<details>
<summary>If a decision pushes toward any of these, we're rebuilding the thing we sunset</summary>

- Not real-time. Not a served API / webhooks.
- Not a graph DB (Neo4j); no embeddings / vector RAG.
- No private-source ingestion (Gong/Slack).
- Not multi-tenant. Not a product.
- No company *discovery* or identity-validation scoring — you hand it a domain.
- No datapoint store / reconciliation engine.
- **The engine owns no *vertical* taxonomy.** Market verticals (e.g. "Weight Loss") are project-owned, user-driven. It ships only a few *generic, cross-domain* closed sets (industry, offering, market type — see [`TAXONOMIES.md`](../TAXONOMIES.md)).

</details>

## Success criteria

- A cold Cowork session answers *"how do the top N telehealth brands describe + price Sermorelin?"* with cited, fresh data in **one invocation, no hand-holding.**
- A second project hitting an already-captured company pays **~$0 Firecrawl.**
- The store is **legible enough** that a deep-research agent reads it before re-scraping.
- *(Long-term)* a category emits a **market-map-ready dataset** (players × prominence × hotness).
- Brian trusts it enough to use in real brand/strategy calls (the agent-workflows bar).

## Principles

- **Spend on conventions, not infrastructure.**
- **Capabilities are global; opinions — including vertical taxonomies — are project-local.**
- **Derive, don't store**, anything the domain gives you for free.
- **Capture observations, not interpretations — verbatim is gold.** Quote what the page says; don't assert what it means. A verbatim claim can't be fabricated past the grep check, so it's the engine's natural anti-hallucination guard. (Volatile facts are grep-or-`unverified`; the rare prior lands only marked — see SCHEMA.)
- **Name for what it is**, not what it might become — let "Market Intelligence" be earned.
