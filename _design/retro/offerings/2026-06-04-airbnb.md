# Retro — offerings module, Airbnb run (2026-06-04)

First **non-telehealth** `offerings.md` — and first **non-SKU / `Catalog`-marketplace** shape. Run reframed (per
the guided emphasis) to a *marketed platform-feature/service taxonomy*, not a per-SKU roster
([`store/airbnb-com/offerings.md`](../../../store/airbnb-com/offerings.md): 7 families → ~24 leaves, lint-clean).

- **Bent the spine at every leaf — held structurally, strained semantically.** `Kind` collapsed to `family`(vertical)/`buyable`(leaf), but "buyable" is a lie for the free/bundled lines (AirCover, AI features, Airbnb Setup) and the "Coming soon" service types. `Visibility` forced `on-request` onto coming-soon rows (no price because *not launched*, not because *gated* — wrong reason, accepted token), and `published` onto free features. `Slug`: ~18 of 24 leaves have no canonical URL → `(no PDP — Tag:8949)` / `(no PDP — Instacart, in-app)`; the lint only checks non-blank so it passed, but "slug = within-company key" is near-meaningless when most rows are `(no PDP …)` and the one *real* stable key (the `service_type_tag` ID) is buried inside that string, not first-class. Price `—` for families + partner discounts ($0 delivery, $10 off) grepped fine.
- **Added nothing to the spine — by choice, and that was right.** Resisted a `Status`/`Category` column; folded live-vs-coming-soon, "X available" counts, and partner name into `What`. Keep local. The one *recurring* axis worth watching (not yet generalizing on n=1): an **availability/Status** dimension (live | coming-soon | rolling-out) — any roadmap-marketing company has it, but `What` holds it for now.
- **OFFERINGS.md silent at two exact spots for a non-SKU shape:** (1) `Kind`'s closed set `family | buyable` has **no value** for a free/bundled feature or an unlaunched line — I guessed "buyable = leaf." (2) `Slug`'s rule ("the offering's relative URL = its within-company key … `(no PDP — …)` for a card without one") assumes URL-keyed is the *norm* and no-PDP the exception; on a marketplace taxonomy the ratio **inverts** and the doc gives no steer on what the key should be when a stable non-URL id (tag/partner) exists.
- **One change:** add a short **"`Catalog`/marketplace shape" note** to OFFERINGS.md that *blesses what I improvised* — when `portfolio_shape: Catalog`, the roster is a marketed-taxonomy read (Portfolio overview is the main content, per the existing Catalog line), `Kind` reads family/leaf, and a leaf's key may be a stable non-URL id written `(no PDP — <tag/partner>)`. Cheaper and truer than adding `Kind`/`Visibility` values; stops the next non-Rx run re-guessing.
- **Verdict:** fit *enough* — spine survived, lint green — but I was furnishing a per-SKU frame with non-SKU content; ~70% fit, semantics strained at `Kind`/`Slug`/`Visibility` on every leaf. The module **stretched without tearing**; one doc note closes most of the gap.
