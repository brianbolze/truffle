# web-research vision (2026-05-29)

> ## **The vision**
> A **project-agnostic company-research engine.** Turn *"research company X"* into reliable, cached, structured intelligence — using **Firecrawl** for capture (not lazy / blocked / JS-walled WebSearch) and **Claude Max** for reasoning (no per-call LLM economics), with a **shared store any project can read**.
>
> **Litmus test for any capability:** *Does this make Claude materially better at understanding a company than someone with generic Claude + WebSearch would be — and is the work reusable across every project, not bound to one venture?*

*Working draft. Trail-shaped — expect iteration. Authored 2026-05-29 from a framing session with Brian, borrowing the substrate philosophy from [Teleprescribe `agent-workflows`](../../Text%20Files/Teleprescribe%20Venture/) and the intellectual core (provenance, freshness, structure-for-retrieval) from [Doro](https://www.brianbolze.com).*

## TL;DR

A global toolbox of **company-research capabilities** that any Claude Code project can invoke. The unit of reuse is no longer "a Teleprescribe workflow" — it's "a company-research capability *any* project calls." A company captured once (for Teleprescribe) is warm and nearly free for the next project (Drift, a PE look, anything).

- **Substrate** (from agent-workflows): markdown + YAML + git + Claude Code/Routines. Cost absorbed by Max. Propose-don't-write. Git is the audit trail.
- **Core ideas** (from Doro, kept lightweight): provenance on every fact, freshness/recency weighting, source-quality ranking, AI-at-ingestion (structure on capture, not on every query).
- **What's deliberately dropped:** Postgres/S3/Temporal, embeddings/fuzzy retrieval, multi-tenant schemas, the full datapoint reconciliation engine, sub-200ms query paths. Bounded, single-user, file-first.

## Why this exists — the gap the two priors leave open

| | Doro | agent-workflows | **web-research (this)** |
|---|---|---|---|
| Proved | The *intellectual core* — entity-centric, AI-at-ingestion, provenance + reconciliation | The *substrate* — markdown/git/Notion + Claude Code/Routines, Max-absorbed cost | Substrate + core ideas, kept light, made **global** |
| Cost model | Per-call LLM SaaS economics | Max subscription absorbs reasoning | Same — but Firecrawl is real per-call $, so **the cache is the budget** |
| Reuse boundary | A product | One venture's domain + KB | **Any project**, project-agnostic |
| Weakness | Heavy infra (Postgres/S3/Temporal) | Bound to Teleprescribe's schema, Notion, KB routing | TBD — keep it from re-becoming Doro |

## Architecture — three layers, different homes

| Layer | What | Lives in | Lifecycle |
|---|---|---|---|
| **Verbs** | Skills / slash commands (`/research-company`, `/refresh-company`, `/map-site`) | Global `~/.claude/skills/` | Versioned with dotfiles; invokable from *any* project, anywhere |
| **Engine + Store** | Firecrawl wrappers, cleaning/pruning scripts, the **shared store**, global default schema | **This repo** | Own GitHub remote + iCloud-synced; commits are the audit trail |
| **Project config** | Schema overrides, source rankings, freshness TTLs, destination (e.g. a Notion DB) | Optional `.web-research/config.yaml` in each project | Per-project; **augments / overrides** global defaults |

**How a global skill reaches the engine.** The skill reads `WEB_RESEARCH_HOME` from `~/.claude/settings.json` — the same file that grants Read/Write/Bash on this repo's path and allowlists `api.firecrawl.dev`. One file: path + permission. Config resolution is a merge: **global defaults (repo) ← project overrides (`.web-research/`)**. A session in `Drift/` with no config gets sensible defaults; one with a config gets its own schema and destination.

## The clever shortcut — domain-as-entity-key

Doro's hardest, most expensive problem was **entity resolution** (RapidFuzz + embeddings + LLM judgment to decide "is this the same company?"). For companies we mostly don't need it: **the canonical domain is the unique key.** Store keyed by domain slug sidesteps identity reconciliation entirely. We keep Doro's *provenance + freshness*; we drop its *identity machinery*.

*(Edge cases — rebrands, M&A, multi-domain companies — are deferred. When they bite, a thin `aliases:` list in the profile frontmatter handles 90% without resurrecting the embedding pipeline.)*

## Store layout

One company = one folder = its whole story. Structured docs at the top are the **latest view** (you rarely dig into `captures/`).

```
store/<domain-slug>/              # e.g. hims-com
  profile.md                      # generic company profile (Synthesis) — frontmatter w/ per-section freshness + provenance
  brand.md                        # optional analysis doc (positioning, voice) — added on demand
  traction.md                     # optional per-company traction signals
  captures/
    2026-05-29/                   # one self-contained folder per run
      homepage.md  pricing.md     # cleaned observations (Capture)
      .payloads/                  # raw Firecrawl JSON + screenshots (gitignored, progressively pruned)
    _archive/                     # old runs swept here by the prune script to keep latest obvious

cohorts/<category-slug>/          # (future) cross-company / category-level signals that don't key on a domain
  traction.md                     # AIO rank, Reddit voice, etc.
```

**Layout principles**
- **"Latest" needs no symlink.** Top-level structured docs are the current view; `profile.md` frontmatter carries `latest_capture: <date>` as a pointer. Symlinks are fragile across iCloud + git + cloud routines — avoided on purpose.
- **Top = Synthesis, `captures/` = Capture.** The agent-workflows operations vocabulary made spatial. Multiple synthesis docs per company are fine and expected (`profile.md`, `brand.md`, later `pricing.md`, `tech-stack.md`).
- **Payload sidecars are write-once durable inputs.** Raw Firecrawl JSON + screenshots ride along on the same 1-credit scrape (markdown/html/rawHtml/links/screenshot are free; only `json`/`query`/enhanced-proxy add credits). Gitignored, iCloud-synced, pruned on a progressive curve (recent: all → weekly → monthly anchors; earliest per company: kept forever).
- **Two entity types, by design.** Companies (keyed by domain) and cohorts (keyed by category slug). v1 is **company-only**; cohorts are the home for the per-category traction signals that don't attribute to a single domain.

## Vocabulary — operations (borrowed from agent-workflows)

| Operation | What it does | Here |
|---|---|---|
| **Capture** | Pull + persist external signal with provenance | Firecrawl map → scrape key pages → cleaned observation in `captures/<date>/` |
| **Enrichment** | AI-at-ingestion: structured fields extracted from captures | `profile.md` fields, populated once at capture, not re-inferred per query |
| **Synthesis** | Derived view across captures (+ optional new sources) | `profile.md` / `brand.md` body; later, cross-company comparisons |
| **Promotion** | Write structured output to a project's KB | Project config's destination (e.g. a Notion DB) — propose-don't-write by default |

## Substrate

*Deliberately lightweight. No heavyweight infra unless a concrete need pushes us there.*

| Decision | Choice | Why |
|---|---|---|
| Persistence | Markdown + YAML frontmatter | Portable, human-readable, git-native, agent-native, iCloud-synced |
| Entity key | Canonical domain slug | Companies have a natural unique key — sidesteps Doro's entity resolution |
| Runtime | Claude Code + Claude Routines | Max plan absorbs reasoning cost; no per-call LLM economics |
| Verbs | Global skills + slash commands | Reusable primitives that compose, invokable from any project |
| External capture | Firecrawl (`/v2/map`, `/v2/scrape`) | Handles JS + bot protection; map-before-scrape controls cost |
| Heavier data | Optional thin SQLite/JSONL | Only when markdown can't carry it (cross-company queries, time-series traction) |
| Embeddings | Skip | Bounded need; domain-as-key removes the main use |
| Cost discipline | Cache + map-before-scrape + freshness TTLs | Firecrawl is the only real $ — the store *is* the budget |

## Design principles

1. **The store is the moat and the budget.** Reasoning is free (Max); Firecrawl is not. Caching, map-before-scrape, and freshness TTLs aren't optimizations — they're the cost model. Second project to research a company should pay almost nothing.
2. **Freshness kills the "out of date" complaint.** TTL-by-section (e.g. pricing 7d, positioning 30d, "what they do" 90d), tunable per project. A capability decides reuse-vs-refetch from the cached freshness, not a guess.
3. **Global capability, project-local opinion.** The generic profile is the 80% everyone wants. *Which* fields matter, how they're ranked, and where they're promoted is the project's call — never baked into the engine.
4. **Provenance on every fact.** Every structured value carries `(source: <url>, captured: <date>)`. Same plumbing serves auditability, freshness, and citable references in ad-hoc sessions.
5. **Propose-don't-write across the boundary.** Writing into a project's KB (Notion, venture markdown) is always proposed-until-reviewed. The engine never silently mutates a consumer's source of truth.
6. **Cloud-routine-ready from day one.** Least-privilege repo, network allowlist carried in-repo. v1 is interactive; scheduled refreshes are a later flip, not a rebuild.

## v1 — on-demand company dossier

`/research-company <domain>` →
1. **Map** the site (`/v2/map`) to discover key pages.
2. **Scrape** key pages (homepage, pricing, products, "how it works") — **cache-aware**: reuse `captures/` if within TTL, refetch if stale.
3. **Enrich** → write/refresh `store/<domain>/profile.md` with provenance + freshness.
4. **Emit a dossier** into the calling project (or this repo's `dossiers/` if ad-hoc).

The store fills as a side effect; the second project to ask about that company gets it warm. Proves the capture → clean → store → synthesize loop end-to-end before generalizing.

## Open questions & deferred

- **Cohort traction** — the per-category signals (AIO rank, Reddit voice, Meta Ad Library) need a non-domain key. Designed-for (`cohorts/`), built later.
- **Cross-company queries** — "compare these N companies on pricing." Markdown carries one company well; a comparison view may want a thin SQLite/JSONL index. Defer until a real ask.
- **Rebrands / M&A / multi-domain** — `aliases:` frontmatter handles most; revisit if it bites.
- **Promotion mechanics** — how a project declares its destination + field mapping in `.web-research/config.yaml`. Design alongside the first project consumer (likely porting Teleprescribe's competitive-intel).
- **Skill ↔ engine contract** — exact interface between the global skill and the repo's scripts (env var resolution, config merge order, error/freshness reporting). First real design task after this doc.
